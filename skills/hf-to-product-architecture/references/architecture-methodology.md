# 架构方法论参考（按需加载）

供 `hf-to-product-architecture` 在需要深度时查阅。方法论本身不进地图——`product/architecture.md` 只落结论要点。

## 1. 复杂度三症状（Ousterhout）

复杂度 = 让系统难以理解或修改的结构属性。三症状即三个对抗方向：

- **变更放大**：一个小改动波及多处 → 用局部性（locality）对抗：相关代码集中一处，修一次处处生效。
- **认知负荷**：完成一件事需要先知道太多 → 用小接口、深模块对抗（词汇见 `hf-codebase-design`）。
- **未知的未知**：不知道该改哪、缺了什么 → 用开发视图约定与关键场景对抗。

比较候选划分时问：一年后，哪种形态的三症状总和最小？

## 2. 架构特征驱动（Ford & Richards）

顺序永远是：特征 → 风格 → 结构。先选风格再找理由是反模式。

- 特征宁少勿滥：3~5 个驱动性特征；「全都要」等于没有驱动力。
- 区分显式特征（领域硬要求：审计、合规、实时性）与隐式特征（普遍底线：可用、安全、简单）；驱动力主要来自显式特征。
- 每条特征配**质量属性场景**（SEI 六要素压成一行）：`<刺激源> 在 <环境> 下 <刺激>，系统应 <响应>，度量: <可观测阈值>`。
  例：「用户在峰值 10 倍流量下提交订单，系统应受理并返回，度量: p95 < 500ms」。
- 写不出可检验场景的特征不是驱动力，是愿望——退回 grill 或记入假设台账。

## 3. 易变性分解（Parnas 信息隐藏 / volatility-based decomposition）

Parnas 的划分标准：每个模块把一个**可能变化的设计决策**藏进内部。列模块时逐问：

- 这个模块封住的变化轴是什么？（计费规则会变、渠道会增、存储会换、同步会变异步……）
- 该变化真发生时，哪些模块**不必**改？答不出来说明缝开错了位置。

易变性的证据来源：grill 访谈结论、假设台账、存量代码热点（`git log` 高频区）、领域常识。无证据的易变性不开缝（与「一个适配器 = 假想接缝」一致）。

反模式：按名词 × 技术层切蛋糕（用户/订单/商品 × controller/service/repo）——每个业务变化都纵切所有模块，变更放大最大化。

## 4. 演进式架构与适应度函数（Ford / Parsons / Sadalage）

写进文档的架构会被时间侵蚀；适应度函数把「架构仍成立」变成可验证的断言：

- **自动化**：依赖方向检查（import-linter / dependency-cruiser / ArchUnit）、分层 CI 脚本、性能预算测试、契约测试。
- **评审项**：无法自动化的（如「新代码归属唯一显然」）写成 `hf-review` 检查条目。

落盘格式：`保护的特征 → 校验方式 → 频率（每次 CI / 每次评审 / 定期）`。

**复核触发**是「重开产品架构」的量化条件，写进地图让未来会话知道何时回来。例：日单量超阈值重评读写拆分；模块数超 7 重评上下文合并；新增第二团队重评 ownership 边界。触发未命中则不动作——演进由信号驱动，不由焦虑驱动。

## 5. 权衡、风险与可逆性（ATAM / 单向门）

- **敏感点**：一个决策同时撬动多个特征（引缓存：性能↑ 一致性↓；事件化：解耦↑ 简单↓）。取舍与理由写明，敏感点进 ADR。
- **风险**：当前最可能让架构返工的 1~3 件事，宜排进最早的关键场景验证——行走骨架的天然内容。
- **可逆性**：双向门快速默认记台账；单向门（存储引擎、事件契约、对外 API、多租户模型）放慢并按 ADR 三条件进 `docs/adr/`。最后责任时刻（LRM）之前不锁死，但用接缝把推迟的决策隔离成局部——拖延不应变成扩散。

## 6. 视图裁剪（4+1 / C4）

默认合并为逻辑（模块与依赖）、开发（目录与放置）、场景（端到端路径）三块。C4 的缩放纪律：本阶段只画「系统 → 模块/上下文」级，组件级留给特性架构。部署拓扑或并发模型成为硬约束时，才补物理/过程视图并记 ADR。
