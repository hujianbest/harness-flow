# 手册：独立评审怎么做

> 本手册是建议，不是约束。偏离它不需要批准；违反宪法不变量则不行。

不变量 6 只规定：完成的宣告必须经受未参与产出的视角检验，结论落盘 `work/<slug>/review.md`。本手册解释为什么以及怎么做。

## 为什么作者不能自评

产出与检验共享同一个上下文时，检验会继承产出的全部盲点——会写假测试的模型同样会写假的"评审通过"。独立性不是仪式，是唯一能打破盲点继承的手段。

## 有效的独立视角

- **subagent / 全新会话**：给评审者的输入只有磁盘上的东西（intent.md、signal.md、diff、evidence/），不给作者的推理过程。评审者应当自己重跑信号，而不是采信日志的转述。
- **用户本人**：用户实际使用产品并给出反馈，是最高效力的评审。

同一会话里"换个角度再看一遍"是降级路径：可以用来找问题，但结论不能是"通过"，只能是"待独立复核"。

## 给评审者的提示词骨架

```
你是独立评审者，与作者无共享上下文。仓库路径 <path>，工作线 work/<slug>。
1. 读 product/intent.md 与 work/<slug>/signal.md，判断信号是否真正证伪了目标；
2. 自己重跑信号命令与 harness.py check，不采信任何叙述；
3. 读 git diff，找正确性、安全、可维护性问题；
4. 结论写为：通过 / 需修改（附逐条 findings），说明你实际运行了什么。
```

## review.md 建议包含

评审方式（subagent/新会话/用户/降级）、评审者实际运行过的命令、findings 清单、结论。"需修改"时作者只修 findings 再送评，不趁机夹带新范围。
