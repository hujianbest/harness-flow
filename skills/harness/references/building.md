# 手册：构建——增量与信号

> 本手册是建议，不是约束。偏离它不需要批准；违反宪法不变量则不行。

构建阶段宪法只要求三件事：先立信号（不变量 3）、主张有证据（不变量 2）、主线常青（不变量 4）。怎么满足它们是你的自由，下面是被验证过好用的方式。

## 写好 signal.md

一份好信号让"完成"变成机器可判定的事实。写之前问自己：**如果这条工作线其实失败了，什么输出会暴露它？**

- 信号要能失败。实现之前先跑一次信号，确认它此刻确实失败（红），才能证明之后的通过（绿）是你的改动带来的。用 `harness.py run` 把红与绿都留证。
- 形式匹配工作的性质：逻辑变更 → 自动测试；UI → 渲染截图 + 核对清单；性能 → 带阈值的基准命令；缺陷修复 → 先有一个能复现缺陷的命令。
- 信号覆盖行为边界，而不是实现细节。换一种实现方式信号仍应成立。

## 增量的节奏

- **一次一个可验证的增量**：每个增量结束时信号可跑、主线常青。增量大小自定，但"三天没跑过验证入口"通常意味着增量切太大。
- **原型自由**：探索性代码随便写、随便扔，不需要信号也不需要证据——只有当它要进主线时，不变量才生效。
- **顺序自定**：风险最高、最能证伪方案的增量优先，往往比"按依赖顺序"更省时间。

## 计划的形态

宪法不要求计划文件。经验上：改动跨越两个以上模块、或触碰数据/安全/公共接口时，先在 `work/<slug>/` 里写一页设计草稿并请独立视角评审一次，返工成本远低于写完再评。单点小改则直接动手，signal.md 就是全部计划。

## 常见陷阱

- 信号在实现之后补写——那是给答案配题目，不变量 3 的意义就没了。
- 改完代码不重跑信号就宣告完成——最新一次证据必须晚于最后一次改动。
- 为了让信号变绿而修改信号——允许，但把理由写进 decisions.md，这本质上是一次范围决策。
