# Shape(塑形:产品定义)

目标:把一个欠定的想法变成**可以开始设计的最小决策集**,而不是一份大而全的 PRD。在获得第一次真实反馈(用户体验到运行中的产品)之前,详尽规格的边际价值极低、幻觉风险极高——所以塑形只回答四个问题,把其余决策推迟到有依据的时候。

> 软件工程对应:需求工程的问题域部分(产品定义)。先钉死"为谁、解决什么、成功长什么样、不做什么",后面的架构与拆解才有判准。

## 流程

### 1. 初始化产品层

```bash
python3 skills/hf-workflow/scripts/hf_gate.py init
```

生成 `product/` 五文件模板(已有文件不覆盖)。

### 2. 结构化访谈

只围绕四个问题,**合并成尽量少的轮次**,不搞 50 连问:

1. **给谁用**:目标用户是具体的谁?(拒绝"所有人";让用户描述一个真实场景里的一个人)
2. **解决什么问题**:现状哪里痛?不用这个 APP 时用户怎么办?
3. **成功长什么样**:第一版做到什么程度算成了?(可观察的信号,如"能完成一次完整的 X")
4. **明确不做什么**:第一版排除什么?(防范围蔓延的唯一手段是把"不做"写下来)

用户答不上来的问题,**给带默认值的选项让用户挑**,而不是开放式追问;用户仍不表态 → 取默认值记入 `assumptions.md`,继续推进。

### 3. 写 product.md 并确认

填写 `product/product.md`(愿景、目标用户、成功标准、MVP 边界、不做清单),预算 ≤60 行。向用户呈现一屏摘要(标注哪些是默认假设),用户确认后写 `- 用户确认: <日期>`;auto 模式可写 `auto-approved <日期>`,前提是所有替用户做的选择已入台账。

确认后进入 `hf-architect`——技术栈、系统草图与切片拆解都在那里完成;`check --product` 在 architect 收尾时运行。

## 假设台账纪律

- 遇到欠定点的标准动作:**提出带默认值的选项 → 记一条 `A-<n> <日期> [生效] <假设> — 默认理由: <一句话>` → 继续**。禁止静默填补,也禁止因等待答复而停摆。
- 用户确认某假设 → 状态改"已确认",内容迁入 `decisions.md`;用户推翻 → 状态改"已推翻",评估波及面,回受影响的阶段受控返工。
- 台账是给用户随时翻看的:每次向用户汇报时,新增假设要点名提示。

## 红线

- 访谈变成问卷轰炸,或反过来一个问题都不问就开写
- 产出几十页 PRD、用户画像、竞品分析(塑形只装最小决策集)
- 为填模板发明用户数据、市场数字、性能指标
- 把未经确认的假设写成 decisions.md 里的已确认决策
- 在本阶段做技术选型、画架构或切 backlog(那是 hf-architect 的事)
- 产品定义未经用户确认就进入架构阶段
