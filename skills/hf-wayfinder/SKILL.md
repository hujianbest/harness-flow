一个松散的想法出现了——它对单次 Agent 会话而言过于庞大，而且笼罩在迷雾中：从这里通往**目的地**的道路尚不可见。寻路的重点是找到这条道路，而不是径直冲向目的地。本技能会在仓库的议题跟踪器上将道路绘制成一张**共享地图**，然后逐一处理其中的**决策票据**——解决结果是决策的问题，而不是要执行的构建切片——直到路线清晰。

每项工作的目的地各不相同，而为它命名是绘制地图的第一步——它决定每张票据的形态。目的地可能是一份需要交接并迭代的规格、一项在规划开始前必须敲定的决策，也可能是一项就地实施的变更，例如数据结构迁移。地图与领域无关——工程工作、课程内容，或任何符合这种形态的工作都适用。

## 规划，而非执行

寻路默认用于**规划**：每张票据解决一项决策；当道路清晰时，地图即告完成——在有人着手执行之前，已经没有待决定的事项。想要直接动手执行的冲动，通常意味着你已经到达地图边缘，该进行交接了。某项工作可以在其 **Notes** 中覆盖这一默认行为——把执行也纳入地图本身——但若无此说明，应产出决策，而不是交付物。

## 以名称指代

每张地图和每张票据都是一个议题，因此都有一个**名称**——也就是标题。在人类阅读的所有内容中——叙述、地图的 Decisions-so-far——都要用名称指代它，绝不能只使用裸标识符、编号或短标识。满墙的 `#42, #43, #44` 难以阅读；名称则一目了然。标识符和 URL 并不会消失——名称会包裹其链接——但它们应位于名称_之内_，绝不能代替名称。

## 地图

地图是该仓库议题跟踪器上的单个议题，带有 `wayfinder:map` 标签——它是规范工件。地图的票据是它的子议题。

地图是**索引**，不是存储库。它列出已经做出的决策，并指向保存详细内容的票据；一项决策只存在于一个位置——它的票据——因此地图绝不复述决策，只概括要点并提供链接。

**地图、子票据、阻塞关系和前沿查询的实际存放位置取决于跟踪器。**议题跟踪器应该已经提供给你——如果没有，请运行 `hf-setup-skills`。查阅跟踪器文档中的“寻路操作”章节，了解_此_仓库如何表达这些内容。如果没有提供跟踪器，默认使用本地 Markdown 跟踪器。

### 地图正文

这是低分辨率的完整地图，每次会话只加载一次。开放票据**不会**列在其中——它们是开放的子议题，通过查询获取。

```markdown
## Destination

<说明到达这张地图终点时的状态——本项工作要寻找道路通往的规格、决策或变更。用一两行说明；每次会话在选择票据前都以此确定方向。>

## Notes

<领域；每次会话都应查阅的技能；本项工作的长期偏好>

## Decisions so far

<!-- 索引——每张已关闭票据占一行：内容足以判断相关性，随后可打开链接查看票据中保存的详细信息 -->

- [<已关闭票据的标题>](link)——<用一行概括答案要点>

## Not yet specified

<!-- 参见“战争迷雾”：范围内但尚无法形成票据的迷雾；随着前沿推进而转化 -->

## Out of scope

```

### 票据

每张票据都是地图的一个**子议题**；跟踪器的议题标识符就是它的身份。票据正文是问题，规模应适合一次包含 100K 个词元的 Agent 会话：

```markdown
## Question

<这张票据要解决的决策或调查>
```

每张票据都带有一个 `wayfinder:<type>` 标签——`hf-research`、`hf-prototype`、`hf-grilling`、`task` 之一（参见[票据类型](#ticket-types)）。

会话通过将票据分配给推动地图的开发者来**认领**票据，而且必须在任何工作开始**之前首先**完成认领，使并发会话能够跳过它。受理人_就是_认领标记：开放且未分配的票据即为未认领。

阻塞使用跟踪器的**原生**依赖关系——这一点至关重要，因为它能在跟踪器自身的 UI 中_直观_呈现前沿，使人类无需打开地图就能看到哪些票据可领取。只有缺少原生阻塞功能的跟踪器才退回使用正文约定。当所有阻塞某张票据的票据都已关闭时，该票据即为**未阻塞**；**前沿**是开放、未阻塞且未认领的子议题——已知范围的边缘。

答案不属于正文——它会在解决时记录（参见[逐步处理地图](#work-through-the-map)）。解决票据期间创建的资产应从议题中链接，而不是粘贴进去。

<a id="ticket-types"></a>
## 票据类型

每张票据要么是 **HITL**——人在回路中，与能够代表自己发言的人类_共同_处理——要么是 **AFK**，由 Agent 独立推动。HITL 票据只能通过这种实时交流解决；Agent 绝不能代替人类的一方发言（如果负责追问的 Agent 自己回答自己的问题，就违反了这一规则）。

- **研究**（AFK）：阅读文档、第三方 API 或知识库等本地资源，以查明某项决策所等待的事实。由 `hf-research` **子 Agent** 解决。当需要当前工作目录以外的知识时使用。
- **原型**（HITL）：制作成本低廉、粗糙但具体的工件供讨论和反馈，从而提高讨论的保真度——可以是提纲、粗略方案、存根，或通过 `hf-prototype` 技能制作的 UI 或逻辑代码。将原型作为资产链接。当关键问题是“它应该是什么样子”或“它应该如何运作”时使用。
- **追问**（HITL）：对话。默认情况。始终调用 `hf-grilling` 和 `hf-domain-modeling` 技能。
- **任务**（HITL 或 AFK）：在能够做出_决策_之前必须完成的手动工作——没有需要决定、制作原型或研究的内容，但在完成这项工作之前讨论会被阻塞。例如注册某项服务以便评估其 API、配置访问权限、移动数据以便查看其形态。这是唯一一种重在_执行_而非决策的类型——它之所以应被纳入，是因为它能解除对决策的阻塞，而不是因为它交付了目的地。Agent 在力所能及之处独立推动（AFK）；否则就向人类提供一份精确的检查清单（HITL）。工作完成时即告解决；答案会记录完成的工作和由此得到的所有事实（凭据位置、新 URL、行数），供后续票据依赖。

## 战争迷雾

地图_有意_保持不完整：不要绘制尚不可见的内容。活动票据之外是**战争迷雾**——你知道某些决策和调查即将出现，却因为它们依赖于仍未解决的问题而无法准确界定，只能看到模糊轮廓。解决一张票据会清除它前方的迷雾，把此时已经可以明确说明的内容逐一转化为新票据，直到通往目的地的道路清晰且没有票据剩余。

地图的 **Not yet specified** 章节用于记录这种模糊轮廓：推测的问题、稍后需要重新审视的区域。它是_通往_目的地但尚未探索的前沿——这里的一切都在范围内，只是还不够明确，无法形成票据。根据当前视野允许的程度，可以写得宽泛，也可以写得详尽；它同时也是路标，让协作者了解本项工作的前进方向。

**迷雾还是票据？**判断标准是你现在能否准确陈述问题，_而不是_现在能否回答它。

- **应创建票据的情况**：问题已经足够明确——即使它处于阻塞状态，你暂时无法处理。
- **应放入 Not yet specified 的情况**：你还无法如此明确地表述问题。不要预先把迷雾切成票据大小的碎片：它的粒度比票据更粗；当前沿抵达时，一片迷雾可能转化为多张票据，也可能一张都不产生。

**Not yet specified** 不包括已经决定的事项（Decisions so far）、已经成为活动票据的事项，以及范围外事项（下一节）。

## 范围外

迷雾只会聚集在_通往_目的地的方向上。目的地确定范围，因此超出目的地的工作属于**范围外**——它不是迷雾，也不属于 **Not yet specified**。它在地图上有自己的 **Out of scope** 章节：你有意识地从_本项_工作中排除的事项。决定它位于这里的是范围，而不是明确程度。

范围外工作绝不会转化——前沿止于目的地——因此只有重新绘制目的地时它才会回归，而且届时应作为一项全新的工作，而不是恢复旧工作。

判定某项内容超出范围是一项范围界定行为，而不是路线上的一步。当一张已经存在的票据被发现位于目的地之外——绘图时被错误纳入范围，或在解决其他票据后才暴露——应**关闭它**（已关闭票据明确不在前沿上），并在 **Out of scope** 章节留下一行：概述其要点和超出范围的原因，并链接到已关闭的票据。它不应进入 **Decisions so far**；该章节记录实际走过的路线，而范围边界并不是路线上的一步。

## 调用方式

有两种模式。无论采用哪种模式，**每次会话绝不能解决超过一张票据**——研究票据除外。

### 绘制地图

用户用一个松散的想法调用本技能。

1. **命名目的地。**运行一场 `hf-grilling` 和 `hf-domain-modeling` 会话，明确这张地图要寻找道路通往什么——规格、决策或变更。目的地会确定范围，因此必须先确定目的地。
2. **绘制前沿。**再次进行追问，这次采用**广度优先**：在整个空间中展开，而不是深入任何一条线索，从而揭示未决决策和当前可采取的第一步。**如果没有发现任何迷雾**——通往目的地的道路已经清晰，整个旅程足够小，可以在一次会话中完成——就不需要地图。停下来，询问用户希望如何继续。
3. **创建地图**（标签为 `wayfinder:map`）：填写 Destination 和 Notes，保持 Decisions-so-far 为空，并将迷雾勾勒到 **Not yet specified** 中。
4. 将**当前能够明确说明的票据创建为地图的子议题**，然后在**第二遍**连接阻塞边（议题需要先拥有 id，才能相互引用）。连接操作会将它们分入前沿和阻塞集合；所有尚无法明确说明的内容都留在迷雾中——即 **Not yet specified** 章节。
5. **启动研究子 Agent。**对于刚刚创建的每张 `hf-research` 票据，启动一个 `hf-research` 子 Agent 并行解决，将其发现记录到一次性的 `research/<name>` 分支，并从票据提供上下文指针。
6. 停止——绘制地图是一次会话的工作；它本身不手动解决任何票据。

<a id="work-through-the-map"></a>
### 逐步处理地图

用户使用一张地图（URL 或编号）调用本技能。票据是**可选的**——如果没有指定票据，由你而不是用户选择下一项决策。

1. 加载**地图**——低分辨率视图，而不是每张票据的正文。
2. 选择票据。如果用户指定了一张，就使用它。否则按顺序选择第一张前沿票据。**认领它**：在开始任何工作前将其分配给自己。
3. 解决它——**按需放大**：需要时获取任何相关票据或已关闭票据的完整正文；调用 `## Notes` 区块中指定的技能。如有疑问，使用 `hf-grilling` 和 `hf-domain-modeling`。
4. 记录解决结果：将答案发布为**解决评论**，**关闭**议题，并向地图的 Decisions-so-far **追加一个上下文指针**。
5. 添加新浮现的票据（先创建，再连接）；把答案促使其变得可明确说明的迷雾转化为票据，并从 **Not yet specified** 中清除每片已转化的内容，使其只存在于对应的新票据中。如果答案表明某张票据——当前票据或另一张票据——位于目的地之外，应**将其判定为范围外**，而不是在路线中解决它。如果该决策使地图的其他部分失效，更新或删除相应票据。

用户可能并行处理未阻塞的票据，因此应预期其他会话会同时编辑跟踪器。
