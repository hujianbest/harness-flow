# 分诊

让项目议题跟踪器中的议题在一个小型分诊角色状态机中流转。

如果此仓库将外部拉取请求视为请求入口（见议题跟踪器配置），分诊也涵盖它们：**PR 是附带代码的议题**——角色、状态和状态机均相同，仅有少数差异在下文标为“对于 PR”。根据跟踪器配置，将单独的 `#42` 解析为议题或 PR。

分诊期间发布到议题跟踪器的每条评论或每个议题都**必须**以此免责声明开头：

```
> *此内容由 AI 在分诊期间生成。*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md)——如何编写持久有效的智能体简报
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)——`.out-of-scope/` 知识库的工作方式

## 角色

两种**类别**角色：

- `bug`——某项功能已损坏
- `enhancement`——新特性或改进

五种**状态**角色：

- `needs-triage`——维护者需要评估
- `needs-info`——等待报告者提供更多信息
- `ready-for-agent`——规格完整，可交给离线智能体
- `ready-for-human`——需要人工实现
- `wontfix`——不会采取行动

对于 PR，同样的状态要结合附带代码来理解：`ready-for-agent` 表示已附上简报，应由智能体对差异执行下一步；`ready-for-human` 表示已准备好由人工合并。

每个已分诊议题应恰好带有一个类别角色和一个状态角色。如果状态角色冲突，请标明冲突，并在执行任何其他操作前询问维护者。

这些是规范角色名称——议题跟踪器中实际使用的标签字符串可能不同。你应当已经获得映射；如果没有，请运行 `hf-setup-skills`。

状态转换：无标签议题通常先进入 `needs-triage`；然后再转入 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。报告者回复后，`needs-info` 返回 `needs-triage`。维护者可以随时覆盖——标明看起来异常的转换，并在继续前询问。

## 调用

维护者调用 `hf-triage`，并用自然语言描述他们想要的操作。解释请求并执行。示例：

- “显示所有需要我关注的内容”
- “我们看看 #42”（议题或 PR）
- “将 #42 移到 ready-for-agent”
- “有哪些内容已准备好让智能体接手？”

## 显示需要关注的内容

查询议题跟踪器，并按最早优先展示三个分组：

1. **无标签**——从未分诊。
2. **`needs-triage`**——正在评估。
3. **自上次分诊备注后报告者有活动的 `needs-info`**——需要重新评估。

当 PR 在范围内时，将外部 PR 纳入这些分组，并为每行标记 `[PR]` 或 `[issue]`。发现流程只展示*外部* PR（跟踪器配置定义何者算外部）——协作者正在进行的 PR 不是分诊工作。此过滤器仅用于发现；无论作者是谁，明确指定的 PR 始终要进行分诊。

显示数量，并为每项提供一行摘要。让维护者选择。

## 分诊指定议题或 PR

1. **收集上下文。**读取完整议题或 PR（正文、评论、标签、作者、日期；对于 PR 还要读取差异）。解析以往的分诊备注，以免重复询问已解决的问题。使用项目领域术语表探索代码库，并遵守该区域的 ADR。对代码库执行两项检查：(a) **重复性**——按领域概念（而不仅是请求的措辞）搜索请求行为的现有实现，并报告搜索位置。如果找到，则这是已实现的 `wontfix`（第 5 步）。(b) **以往拒绝**——读取 `.out-of-scope/*.md`，并展示任何与此请求相似的内容。

2. **提出建议。**向维护者说明你建议的类别和状态及其理由，并提供与请求相关的简短代码库摘要——包括是否已经实现。等待指示。

3. **验证主张。**在任何追问前，检查该主张是否成立。对于 bug，按照报告者的步骤复现。对于 PR，确认差异实现了其声称的内容——检出它，并运行相关测试或命令。报告结果：已确认（附代码路径）、失败或细节不足（强烈的 `needs-info` 信号）。经过确认的验证能让智能体简报更有力。

4. **追问（如有需要）。**如果请求需要充实，同时运行 `hf-grilling` 和 `hf-domain-modeling` 技能——每轮提出一组问题，逐步将其打磨成形；在决策落定时明确领域术语，并就地更新 `CONTEXT.md`/ADR。

5. **应用结果：**
   - `ready-for-agent`——发布智能体简报评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human`——使用与智能体简报相同的结构，但注明无法委派的原因（需要判断、外部访问、设计决策、手动测试）。
   - `needs-info`——发布分诊备注（模板见下文）。
   - `wontfix`——关闭，并根据*原因*选择评论：
     - **已实现**——该变更已存在于代码库中。指出其所在位置；**不要**写入 `.out-of-scope/`（该知识库用于*被拒绝*的请求，而不是已构建的请求）。
     - **已拒绝（bug）**——礼貌说明，然后关闭。
     - **已拒绝（enhancement）**——写入 `.out-of-scope/`，在评论中链接该文件，然后关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage`——应用该角色。如有部分进展，可选择添加评论。

## 快速状态覆盖

如果维护者说“将 #42 移到 ready-for-agent”，请信任他们并直接应用该角色。确认即将执行的操作（角色变更、评论、关闭），然后行动。跳过追问。如果未经追问会话就移到 `ready-for-agent`，询问他们是否想编写智能体简报。

## Needs-info 模板

```markdown
## 分诊备注

**目前已确定的内容：**

- 要点 1
- 要点 2

**仍需你提供的内容（@reporter）：**

- 问题 1
- 问题 2
```

将追问期间解决的所有内容记录在“目前已确定的内容”下，以免工作丢失。问题必须具体且可执行，不能只是“请提供更多信息”。

## 恢复之前的会话

如果议题或 PR 中已有以往分诊备注，请读取它们，检查报告者是否回答了任何未决问题，并在继续前展示更新后的情况。不要重复询问已解决的问题。
