# Skeleton(行走骨架)

目标:第 0 个里程碑是"能跑的空壳"。集成风险(环境、构建、启动、数据通路、部署)要在第 0 天暴露,而不是在第 20 个特性之后;并且从骨架 ship 起,用户就有可体验的东西,反馈循环立即启动——**反馈比规格便宜且准确**。骨架同时是 `product/architecture.md` 的第一次真实验证:架构在文档评审里不被证明,在真实运行里才被证明。

## 执行方式

骨架是一个普通切片,走完整交付链(frame → plan → build → verify → ship),本技能只收紧内容。frame 定格建议:`模式: 建造`、`风险档位: 2`、`用户可感知: 是`、`切片: S-1`。全新项目的环境基线 = 搭起最小测试骨架并跑通一个空测试(见 `hf-frame`)。

## 骨架必须包含

1. **脚手架与仓库初始化**:严格按 `product/architecture.md` 与 decisions/assumptions 台账记录的技术栈和模块边界;偏离 = 先回改地图与台账再动手。
2. **一键命令**:`dev`(本地启动)与 `test`(全量测试)各一条命令,写入 README。做不到一条命令,后续每个切片的验证成本都会翻倍。
3. **一条最薄的真实端到端路径**:优先取 architecture.md 的第一条关键流程,穿透全部关键层(如 UI → 业务逻辑 → 存储 → UI 回显一条真实数据)。占位数据可以,占位层不可以——mock 掉存储层的骨架没有暴露集成风险,不算行走。
4. **用户体验入口**:用户按 README 一条命令能启动并访问(本地地址或预览部署)。
5. **CI(可行时)**:跑 `test` 的最小工作流。平台不可用时记入 progress.md 遗留事项,不阻塞。

## 证据与验收

- `smoke`:真实启动、真实访问一次端到端路径(`hf_gate.py run --label smoke -- <探活命令>`,或渲染截图)。
- `demo`:用户视角的证据——录屏/截图/预览地址探活日志,存 `evidence/demo-*`。
- demo 验收(见 `hf-verify`):向用户交付一句话"怎么打开它"+ demo 证据;用户跑通即接受,落盘 `reviews/demo-acceptance.md`。
- ship 时(见 `hf-ship`)把 backlog 的 `S-1` 勾选,反馈(如"跑不起来""想先看 X 功能")回写产品层。

## 红线

- 骨架里夹带业务功能("顺手把登录做了"——那是 S-2 的事)
- 端到端路径 mock 掉关键层,骨架"走"不起来
- 技术栈或模块结构偏离 architecture.md / decisions.md / assumptions.md 而不回写地图与台账
- 没有一键 dev/test 命令就宣称骨架完成
- 骨架未 ship 就开始功能切片
