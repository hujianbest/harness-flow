# 诊断缺陷

一套用于处理棘手缺陷的严格方法。只有给出明确理由时才能跳过阶段。

探索代码库时，读取 `CONTEXT.md`（如果存在），清晰理解相关模块，并检查所涉及区域中的 ADR。

## 脱敏

本技能会要求你展示命令、输出和捕获的工件。**首先对每项秘密信息进行脱敏**——在原位置写入 `<REDACTED>`。让循环使用环境变量，使凭据留在环境中，而不是出现在你展示的内容里。捕获的工件包含身份验证标头：只引用携带有效信号的行。

如果脱敏后的输出不足以诊断缺陷，要明确说明并询问用户。

## 阶段 1——构建反馈循环

**这就是本技能的核心。**其他一切都是机械性的。如果你拥有一个针对该缺陷的**紧密**通过/失败信号——一个会因_这个_缺陷而变红的信号——你就能找到原因；二分定位、假设检验和插桩都只是利用这个信号。如果没有这样的信号，无论盯着代码看多久都无济于事。

要在这里投入格外多的精力。**积极进取。发挥创造力。绝不放弃。**

### 构建反馈循环的方法——大致按以下顺序尝试

1. 在任何能够触达缺陷的接缝处编写**失败测试**——单元测试、集成测试或 e2e 测试。
2. 针对正在运行的开发服务器使用 **Curl / HTTP 脚本**。
3. 使用夹具输入进行 **CLI 调用**，并将 stdout 与已知正确的快照进行差异比较。
4. 使用**无头浏览器脚本**（Playwright / Puppeteer）——驱动 UI，并对 DOM、控制台或网络作断言。
5. **重放捕获的跟踪记录。**将真实的网络请求、载荷或事件日志保存到磁盘；通过隔离的代码路径重放。
6. **一次性测试支架。**启动系统的最小子集（一个服务、经过模拟的依赖），用一次函数调用执行缺陷代码路径。
7. **属性测试或模糊测试循环。**如果缺陷表现为“输出有时错误”，就运行 1000 个随机输入并寻找失败模式。
8. **二分测试支架。**如果缺陷出现在两个已知状态（提交、数据集、版本）之间，自动执行“在状态 X 启动、检查、重复”，以便使用 `git bisect run`。
9. **差分循环。**让同一个输入分别通过旧版本和新版本（或两种配置），然后比较输出差异。
10. **HITL bash 脚本。**最后手段。如果必须由人点击，就使用 `scripts/hitl-loop.template.sh` 引导_他们_，使循环仍然结构化。捕获的输出会反馈给你。

构建出正确的反馈循环，缺陷就已经解决了 90%。

### 收紧循环

把循环当作产品。一旦拥有_一个_循环，就要将其**收紧**：

- 能否让它更快？（缓存设置、跳过无关初始化、缩小测试范围。）
- 能否让信号更敏锐？（针对具体症状作断言，而不是只断言“没有崩溃”。）
- 能否让它更具确定性？（固定时间、为 RNG 设置种子、隔离文件系统、冻结网络。）

一个耗时 30 秒且不稳定的循环只比没有循环略好；一个耗时 2 秒且具有确定性的循环才算紧密——它是调试的超能力。

### 非确定性缺陷

目标不是获得干净的复现，而是获得**更高的复现率**。循环触发 100 次、并行执行、增加压力、缩窄时序窗口、注入休眠。复现率为 50% 的不稳定缺陷可以调试，1% 则不行——持续提高复现率，直到能够调试。

### 确实无法构建循环时

停下来并明确说明。列出尝试过的方法。向用户请求：(a) 访问任何能够复现问题的环境；(b) 一份经过脱敏的捕获工件（HAR 文件、日志转储、核心转储、带时间戳的屏幕录像）；或 (c) 添加临时生产插桩的许可。没有循环时，**不要**继续提出假设。

### 完成标准——一个能够变红的紧密循环

当循环既**紧密**又**具备变红能力**时，阶段 1 才算完成：你能指出**一条命令**——脚本路径、测试调用或 curl——并且你**已经至少运行过一次**（展示经过脱敏的调用及其输出），同时它满足：

- [ ] **具备变红能力**——它会执行实际的缺陷代码路径，并对**用户描述的确切症状**作断言，因此会因这个缺陷而变红，在修复后变绿。不能只是“运行时不报错”——它必须能够_捕获这个特定缺陷_。
- [ ] **具有确定性**——每次运行都得到相同结论（对于不稳定缺陷，按照上述方法固定在较高复现率）。
- [ ] **快速**——耗时以秒计，而不是以分钟计。
- [ ] **Agent 可运行**——你可以无人值守地运行它；只有通过 `scripts/hitl-loop.template.sh` 才允许人处于循环中。

如果你发现自己在这条命令存在之前就开始阅读代码并构建理论，**立即停止——直接跳到假设正是本技能要防止的错误。**没有具备变红能力的命令，就不能进入阶段 2。

## 阶段 2——复现并最小化

运行循环。观察它变红——缺陷出现。

确认：

- [ ] 循环产生的是**用户**描述的失败模式，而不是恰好发生在附近的另一种失败。缺陷找错 = 修复错误。
- [ ] 该失败可以在多次运行中复现（对于非确定性缺陷，其复现率足够高，可以据此调试）。
- [ ] 已经捕获确切症状（错误消息、错误输出、缓慢耗时），使后续阶段能够验证修复是否确实解决了它。

### 最小化

一旦变红，就把复现场景缩减为**仍然会变红的最小场景**。**每次只移除一项**输入、调用方、配置、数据或步骤，每次移除后都重新运行循环——只保留对失败不可或缺的内容。

这样做的原因是：最小复现会缩小阶段 3 的假设空间（剩下需要怀疑的可变因素更少），并会在阶段 5 成为干净的回归测试。

只有当**剩余的每个元素都不可或缺**时才算完成——移除其中任何一个都会使循环变绿。

在完成复现**并且**完成最小化之前，不要继续。

## 阶段 3——提出假设

在测试任何假设之前，先生成 **3 至 5 个按可能性排序的假设**。只生成一个假设会让你锚定在第一个看似合理的想法上。

每个假设都必须**可证伪**：说明它作出的预测。

> 格式：“如果 <X> 是原因，那么 <改变 Y> 会使缺陷消失，而 <改变 Z> 会使其恶化。”

如果无法说明预测，这个假设就只是感觉——将其丢弃或进一步打磨。

**测试前向用户展示排序后的列表。**他们往往掌握能够立即改变排序的领域知识（“我们刚刚部署了与第 3 项相关的更改”），或者知道哪些假设已经被排除。这是一个成本很低却能大量节省时间的检查点。不要因此阻塞——如果用户处于 AFK 状态，就按你的排序继续。

## 阶段 4——插桩

每次探测都必须对应阶段 3 中的一项具体预测。**每次只改变一个变量。**

工具优先级：

1. 如果环境支持，优先使用**调试器或 REPL 检查**。一个断点胜过十条日志。
2. 在能够区分不同假设的边界处添加**有针对性的日志**。
3. 绝不“记录所有内容然后 grep”。

使用唯一前缀为**每条调试日志添加标记**，例如 `[DEBUG-a4f2]`。这样结束时只需执行一次 grep 即可清理。未标记的日志保留，已标记的日志删除。

**性能分支。**对于性能回退，使用日志通常是错误做法。应先建立基线测量（计时测试支架、`performance.now()`、性能分析器、查询计划），然后进行二分定位。先测量，再修复。

## 阶段 5——修复并添加回归测试

在**修复之前**编写回归测试——但前提是存在一个适合它的**正确接缝**。

正确接缝能够让测试执行调用点处实际发生的**真实缺陷模式**。如果唯一可用的接缝太浅（缺陷需要多个调用方，测试却只有一个调用方；单元测试无法复现触发缺陷的调用链），那么在该处编写回归测试只会带来虚假的信心。

**如果不存在正确接缝，这本身就是一项发现。**将其记录下来。代码库架构使这个缺陷无法被测试锁定。为下一阶段标记这一点。

如果存在正确接缝：

1. 在该接缝处把最小复现转换为失败测试。
2. 观察它失败。
3. 应用修复。
4. 观察它通过。
5. 针对原始的（未经最小化的）场景重新运行阶段 1 的反馈循环。

## 阶段 6——清理和事后复盘

宣布完成前必须满足：

- [ ] 原始复现不再出现问题（重新运行阶段 1 的循环）
- [ ] 回归测试通过（或已记录缺少接缝）
- [ ] 已移除所有 `[DEBUG-...]` 插桩（`grep` 该前缀）
- [ ] 已删除一次性原型（或移至有明确标记的调试位置）
- [ ] 已在提交或 PR 消息中说明最终被证明正确的假设——让下一位调试者能够借鉴

**然后问：什么措施本可以防止这个缺陷？**如果答案涉及架构变更（没有合适的测试接缝、调用方纠缠不清、存在隐藏耦合），就将具体情况移交给 `hf-improve-codebase-architecture` 技能。在修复完成**之后**再提出建议，而不是之前——此时你掌握的信息比开始时更多。
