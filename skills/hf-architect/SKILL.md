# Architect(架构与拆解)

目标:在写第一行代码之前做**最少但足够**的架构决策——恰好够把 MVP 拆成端到端的垂直切片、够让后续每个特性不需要重新理解系统。不做大而全的架构文档:未经运行验证的架构假设越多,返工越贵;S-1 行走骨架才是架构的第一次真实验证,所以架构只画一页,靠骨架当天证伪。

> 软件工程对应:经典生命周期的"架构设计/概要设计"与"需求拆解"。HF 的调整是把"评审文档验证架构"换成"行走骨架运行验证架构",把拆解产物定为可演示的垂直切片而非技术分层的工作包。

前提:`product/product.md` 已有有效的 `- 用户确认:` 行(hf-shape 完成)。

## 流程

### 1. 技术栈决策(带观点的默认值)

让非技术用户做技术选型,是把决策推给信息最少的一方。对照预设直接给出推荐:

| 产品形态 | 默认预设 | 默认理由 |
|----------|----------|----------|
| Web 应用(默认) | Next.js/React + SQLite,单仓 | 一栈到底、本地即跑、预览部署成熟 |
| 纯后端 API | Python FastAPI 或 Node,SQLite→Postgres | 上手快、测试生态好 |
| CLI / 工具 | Python 或 Go 单二进制 | 分发简单、stdlib 够用 |
| 静态站 / 展示页 | 静态生成器 + 托管平台 | 零运维 |

规则:用户明确选择 → 记入 `decisions.md`(D-n);未表态 → 用默认并记入 `assumptions.md`(A-n,状态"生效")。团队既有栈、部署约束等真实约束**压倒**默认预设。选一门本地能跑通验证环路(测试 + 启动)的栈——环境基线跑不通的栈再时髦也不选。

### 2. 系统草图(architecture.md 主体)

按 `product/architecture.md` 模板填写,每节几行、总量 ≤80 行:

- **系统形态**:单体 Web / CLI / API+前端……一行定形。
- **模块边界**:3~7 个模块,各配"职责一句话 + 代码位置"。判准:MVP 边界内的每个能力都能指认落在哪个模块;指认不了说明模块划分或 MVP 边界有一个是错的。
- **核心数据模型**:核心实体与关系,几行即可;字段级细节推迟到特性设计(hf-plan)。
- **关键流程**:1~3 条端到端主流程(入口 → 模块 → 存储 → 出口),S-1 骨架将至少穿透其中一条。
- **横切约定**:错误处理、测试组织、目录布局、命名——新代码必须遵循的约定,由骨架落实。

只为 `product.md` MVP 边界内的需求设计(YAGNI):不为想象中的规模、租户、国际化预留抽象。真实决策点(不止一种合理做法且影响拆解)才做方案对比,并记入 decisions/assumptions;没有就直接写结论。

### 3. 需求拆解(垂直切片 backlog)

把 MVP 边界切成**垂直切片**写入 `backlog.md`:

- 每片端到端可演示(穿透 UI→逻辑→存储的一条真实路径),不按技术分层切("先把数据库都建好"不是切片)。
- 每片能指认落在哪些模块、对应哪条关键流程——指认不了,回改架构或切片。
- `S-1` 固定为行走骨架(见 `hf-skeleton`),之后按"用户价值 ÷ 体量"排序。
- 每片写**演示判据**:交付时用户能看到/做到什么。写不出演示判据的切片说明还没想清楚,拆小或推迟。
- 第一批 3~6 片足够;backlog 是活文档,每次 ship 后按反馈重排。

### 4. 确认与推进

向用户呈现一屏摘要:技术栈(标注哪些是默认假设)、系统形态、模块清单、前几个切片。用户确认后在 `architecture.md` 写 `- 用户确认: <日期>`(auto 模式同 hf-shape 规则),然后:

```bash
python3 skills/hf-workflow/scripts/hf_gate.py check --product
```

PASS 后进入 S-1(读 `hf-skeleton`),RESULT 行记入首个特性的 progress.md。

## 活文档与地图纪律

architecture.md 的第二身份是**代码库地图**,这是主要的 token 节省机制:

- 交付链各阶段(frame 定位改动面、plan 做设计、评审冷读)**先读地图再读相关代码**,不做全库扫描。
- 地图保持 ≤80 行;结构变化(模块边界、数据模型、关键流程、横切约定)由 `hf-ship` 回写,无结构变化不动它。
- 特性级细节(接口签名、字段、任务)永远不下沉到地图——地图答"什么在哪里、约定是什么",不答"具体怎么做"。

## 存量项目用法

存量项目不需要完整产品层,但反复交付时值得单独建一份地图:冷读代码后只创建 `product/architecture.md`(标注"由代码反推"),不要求其余四文件;`status` 会将其识别为"仅架构地图"模式,不触发产品层门禁。首次建立算一次档位 1 的文档改动。

## 红线

- 产出大而全的架构文档(分层图、时序图堆叠)或为未确认的未来需求做设计
- 在地图里写接口签名、字段级表结构、组件树(那是 hf-plan 的特性设计)
- backlog 按技术分层切片、切片没有演示判据、或切片指认不出对应模块
- 技术栈与 decisions/assumptions 台账不一致(选了却不入账)
- 跳过用户确认直接开始骨架,或跳过 S-1 直接做"最有意思的功能"
- 把地图当垃圾场:超过一页、堆积过期内容而不删
